1 System overview

A three-tier app that scores LLM/RAG outputs using DeepEval metrics — an "LLM-as-judge" approach where a Groq or OpenAI model evaluates another model's output. The React SPA collects inputs, the Express gateway validates and forwards them, and the Python/FastAPI sidecar does the actual evaluation by calling DeepEval's metric classes.

Why three tiers instead of the frontend calling Python directly The Express layer is a thin, stateless gateway — it re-validates fields per metric, enforces feature-flag gates (ENABLE_*), normalizes response shape for the UI, and hosts non-eval concerns (Excel parsing, HTML/Excel report generation). No LLM provider keys ever reach Node — only the Python sidecar talks to Groq/OpenAI.

4 Core abstraction: MetricEvaluator & GroqModel

Everything in the sidecar routes through one class, MetricEvaluator (deepeval_server.py:665), constructed fresh per request by init_evaluator_from_env() (line 1508):

1

Reads EVAL_MODEL from env and pattern-matches the prefix to pick a provider: llama-, mixtral-, gemma, qwen, meta-llama, openai/ → Groq; gpt- → OpenAI; anything unrecognized → falls back to Groq llama-3.3-70b-versatile.

2

For Groq, wraps the model in GroqModel (line 329) — a DeepEvalBaseLLM subclass pointing the OpenAI SDK at https://api.groq.com/openai/v1. This is the key compatibility shim: DeepEval's metric classes expect DeepEval's/OpenAI's own model interface, so GroqModel.generate() reimplements structured JSON output and includes a schema-repair fallback (_repair_single_field_schema, line 361) for when a smaller Groq model invents its own JSON field name instead of the one DeepEval's schema requires.

3

For OpenAI, uses DeepEval's built-in GPTModel directly — no wrapper needed.

4

MetricEvaluator.evaluate(metric_name, ...) (line 1391) validates per-metric required fields, builds an LLMTestCase, then dispatches to one evaluate_<metric>() method per metric, each constructing the matching deepeval.metrics.* class with include_reason=True, async_mode=False, strict_mode=False and calling metric.measure(test_case).

Why a new instance per request, not one shared evaluator Token-usage accounting (GroqModel.total_prompt_tokens etc.) is tracked per-instance so the /eval handler can report total_usage scoped to just that request's LLM calls, via _snapshot_usage()/_usage_since() baselining before/after each metric.

Flow 1

Single-turn evaluation — e.g. faithfulness

1
LLMEvalForm.tsx

User fills in metric, query, output, context[], expected_output. validateForm() (components/LLMEval/validation.ts) enforces per-metric required fields before submit.

2
services/llmEvalApi.ts

evaluateWithDeepEval() filters empty context entries and POSTs to http://localhost:3002/api/eval-only.

3
routes/evalRoutes.ts

Checks ENV.ENABLE_SINGLE_TURN; normalizes metric (string / array / "all"); rejects any metric in ENV.DISABLED_METRICS (403); re-validates required fields per metric (output required except for contextual metrics; query required for pii_leakage/bias/hallucination; non-empty context required for hallucination).

4
services/evalClient.ts

evalWithFields() builds the payload and POSTs to ENV.DEEPEVAL_URL (http://localhost:8000/eval).

5
deepeval_server.py — POST /eval

evaluate_llm_response (line 1574) expands "all" to the full SUPPORTED_METRICS list, re-validates fields a third time, calls init_evaluator_from_env() once for the whole request, then loops over requested metrics calling evaluator.evaluate(...) for each, appending a MetricResult to results[].

6
get_verdict_for_metric() — line 485

Maps the raw 0–1 score to a human label using env-configurable HIGH/LOW cutoffs (e.g. FAITHFULNESS_VERDICT_HIGH=0.75 / _LOW=0.3 → FAITHFUL/PARTIAL/NOT_FAITHFUL). Bias, hallucination, and PII leakage are "lower is better" — their HIGH/LOW comparisons are inverted in code.

7

EvalResponse always returns results: MetricResult[], plus legacy top-level metric_name/score/explanation populated from results[0] for backward compatibility.

8
routes/evalRoutes.ts

Extracts verdict/detail/usage from results[0] (single metric) or passes the full results[] through (multi-metric/all).

9
ResponsePanel.tsx

Renders score/verdict/explanation. For faithfulness, the detail object (truths/claims/per-claim verdicts/idk-yes-no counts) drives a claim-level breakdown.

Faithfulness's IDK handling — the most involved metric evaluate_faithfulness() (line 778) asks DeepEval to extract "truths" from context and "claims" from output, verdicts each claim yes/no/idk, then applies IDK_HANDLING (yes/no/count) to decide how ambiguous claims affect the final score. If DeepEval extracts zero claims (a small-model failure mode), it falls back to plain substring matching between output and context.

Flow 3

Custom metrics (G-Eval)

Deliberately isolated from the built-in metrics — its own route file (customMetricsRoutes.ts), its own service functions, and its own sidecar endpoints. This is DeepEval's GEval — free-text criteria evaluated by the judge LLM, rather than a fixed metric class.

  • GET /api/custom-metrics/config?metric_name=correctness — prefills an editable "scoring mechanism" (criteria, evaluation_params, threshold, verdict cutoffs) resolved from CUSTOM_GEVAL_<NAME>_* env vars.
  • POST /api/custom-metrics/geval — accepts optional per-call overrides for criteria, evaluation_steps (mutually exclusive — GEval allows only one), and threshold.
  • Response shape mirrors /eval-only's single-metric shape exactly, so ResponsePanel.tsx and report generation work unchanged for custom metrics too.

Flow 5

Batch evaluation

The only flow driven by a file upload, and the only one that fans out to N independent evaluation calls.

1
ExcelUpload.tsx

multipart/form-data POST /api/batch/upload-excel. multer accepts only .xlsx/.xls, saves to a temp uploads/ dir; excelService.ts#parseExcelFile() reads every sheet via the xlsx package. Temp file deleted ~1s later either way.

2
DatasetPreview.tsx

Renders the parsed sheets.

3
JsonConverter.tsx

Maps sheet rows into evaluation-ready records (query/output/ context/expected_output/a metric column, default name "Metrics").

4
MetricSelector.tsx

Shows required/optional fields per metric — informational only; enforcement happens server-side.

5

POST /api/batch/evaluate (gated by requireBatchEval middleware). For each row: reads the metric from record[metricColumn], normalizes it (lowercase, collapse whitespace/underscores), defaults to answer_relevancy if missing/NA, validates required fields, calls evalWithFields().

6
ReportGenerator.tsx

POST /api/batch/generate-report → generateHTMLReport() (self-contained HTML with inline charts) and/or generateExcelReport() (Summary/Results/Data sheets). reportType: "both" returns both files base64-encoded in one JSON response.

Per-row fault isolation Each row is evaluated independently and sequentially — a per-row try/catch means one failing row (missing field, sidecar error) doesn't abort the batch; it's captured as { rowIndex, error } in the results array alongside successful rows. Token usage is summed across all rows into a totalUsage object.

6 Feature flags

backend/src/config/env.ts defines five independent boolean toggles (default true unless explicitly "false"), plus DISABLED_METRICS. Two layers enforce these: route guards (403 if disabled) and UI tab visibility (App.tsx reads /api/status once on mount).

ENABLE_SINGLE_TURN
Gates /api/eval-only and the Single Evaluation tab.
ENABLE_MULTI_TURN
Gates /api/eval-multiturn and the Multi-Turn tab.
ENABLE_CUSTOM_METRICS
Gates all /api/custom-metrics* routes and the G-Eval tab.
ENABLE_BATCH_EVAL
Gates upload/evaluate/report routes via requireBatchEval middleware.
ENABLE_GOLDEN_DATASET
Gates /api/batch/generate-goldens and the Golden Dataset tab.
DISABLED_METRICS
Comma-separated metric names hidden from dropdowns and rejected server-side if requested directly.

The UI defaults all tabs to enabled before the /api/status fetch resolves (or if unreachable) — route guards are the real enforcement, tab visibility is cosmetic. If the active tab becomes disabled, firstEnabledPage() picks the next tab by priority: llm-eval → batch-eval → multi-turn-eval → golden-dataset → custom-metrics.

8 Known gaps (confirmed in code)

provider is accepted but ignored — every request shape carries a provider field defaulting to "groq", but init_evaluator_from_env() decides Groq vs. OpenAI purely from the sidecar's EVAL_MODEL env var.
Frontend hardcodes http://localhost:3002 in App.tsx and every services/*.ts file rather than reading VITE_API_URL.
llm-eval-providers/.env's PORT=3002 is dead config — deepeval_server.py hardcodes port 8000.
Root package.json's dev:python/start:python scripts point at a nonexistent python/ragas_server.py — leftover from an earlier RAGAS-based layout. Use cd llm-eval-providers && python deepeval_server.py.
No automated test suite for backend, frontend, or the sidecar — validation has been manual API calls (see postman-collection.json).
Report generation's "both" mode returns base64 JSON, not a zip, despite a code comment suggesting a zip was the original intent.
